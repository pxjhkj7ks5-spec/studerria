# Правила роботи з NaradaDruk

Ці правила доповнюють кореневий `AGENTS.md` і застосовуються лише в `services/naradadruk`.

## Межі роботи та активний WIP

- Тримай зміни в межах `services/naradadruk` і явно потрібних для цього сервісу root-файлів (`version.json`, `changelog.json`, `docker/local`, сервісні update-скрипти).
- На початку перевіряй `git status`. У NaradaDruk часто є паралельний незавершений WIP: не перезаписуй, не форматуй масово й не додавай до коміту чужі зміни.
- Перед редагуванням файлу з наявним diff спочатку прочитай diff і збережи обидва наміри. Якщо межа відповідальності неочевидна, зупинись і повідом про конфлікт.
- Для коміту додавай тільки точні файли своєї задачі; не використовуй `git add -A` або інше широке staging за наявності WIP.
- Не перенось NaradaDruk-зміни у Studerria чи інші сервіси без прямої потреби користувача.

## Продукт і інтерфейс

- Основна мова інтерфейсу та повідомлень — українська. Тексти мають бути короткими, природними й готовими для реального покупця або власника магазину.
- Візуальний напрям — `macOS Tahoe / Apple Liquid Glass / iOS 26`, але читабельність, контраст, доступність і швидкість важливіші за декоративні ефекти.
- Зміни storefront перевіряй щонайменше на мобільній і десктопній ширині. Не виправляй desktop ціною поломки mobile і навпаки.
- Адмінські дії мають мати зрозумілий результат, безпечні дефолти та видимий стан помилки. Не показуй покупцям внутрішні ID, технічні помилки, приватні джерела моделей чи службові посилання.
- Для товарів, замовлень, відгуків і аналітики зберігай узгодженість між storefront, адмінкою, API, Prisma та Telegram owner bot.

## Commerce, замовлення та відгуки

- Ціну, знижку, доступність товару й підсумок замовлення обчислюй та перевіряй на сервері з актуальних даних; не довіряй сумам або статусам із клієнта.
- Реквізити для переказу не показуй у відкритому checkout. Усталений потік — власник підтверджує замовлення та передає реквізити покупцю особисто.
- Спочатку надійно збережи замовлення або відгук, потім надсилай Telegram-сповіщення. Збій Telegram не повинен губити основний запис; зберігай статус і безпечний опис помилки для повторної обробки.
- Відгуки проходять валідацію й модерацію; публічний статус, адмінський статус і Telegram-сповіщення мають залишатися синхронними.
- Події аналітики не повинні впливати на успіх checkout чи інших основних дій. Зміни метрик супроводжуй тестами агрегації та перевіркою приватності.

## Telegram, каталог і owner bot

- Звичайні дописи Telegram не є товарами. Автоматичний імпорт обробляє лише дописи з `#товар`.
- Без явного `Публікація: так` товар створюється як чернетка. Публікуй лише валідний товар із фото та коректною ціною або варіантами.
- Коли користувачу потрібен шаблон товару, давай готовий до копіювання формат із `#товар`, назвою, категорією, ціною/варіантами, описом, матеріалом, терміном, доставкою, оплатою та полем публікації.
- Зберігай імпорт і команди ботів ідемпотентними: Telegram channel/message ID, content hash і Prisma-стан мають запобігати дублям та дозволяти безпечний повторний запуск.
- Фото мають зберігатися у постійному `UPLOAD_DIR`, а не залежати від тимчасових Telegram/MakerWorld URL чи шару збірки. Не дублюй однакові зображення.
- `scripts/telegram-catalog-worker.ts` відповідає за канал і каталог; `scripts/makerworld-bot-worker.ts` — за owner workflow, публікацію, маркетплейсні тексти та операційні дії. Не змішуй ці потоки без перевірки всього ланцюжка.
- Для `/makerworld`, `/marketplace` і `/repost` зберігай owner-only доступ, whitelist чатів/користувачів, preflight-перевірки та приватність вихідних MakerWorld-посилань.
- Не змінюй усталений публічний формат Telegram-дописів або маркетплейсного тексту побічно. Якщо задача стосується копірайту, перевір точний фінальний текст і посилання.

## Дані, Prisma та секрети

- Зміни Prisma-схеми проводь крізь увесь ланцюжок: schema, generated client, seed/import, API/server code, tests і Docker startup. Перед інтеграційним запуском worker-а виконай schema push та seed для тестової БД, щоб не отримати `P2021`.
- Не використовуй `docker compose down -v` для звичайної зміни схеми. Видалення volume допустиме лише за прямої потреби повністю відтворити БД або повторно імпортувати дамп.
- Міграції та backfill мають зберігати наявні товари, замовлення, відгуки, аналітику, Telegram sync state і завантажені зображення.
- Секрети не виводь у термінал, diff або відповідь. Для адмін-пароля називай лише ланцюжок `docker/local/.env:NARADADRUK_ADMIN_PASSWORD` → container `ADMIN_PASSWORD` → `process.env.ADMIN_PASSWORD` і перевіряй тільки наявність/непорожність.
- Telegram tokens, owner IDs, chat IDs та інші env-значення перевіряй без розкриття значень. У логах і UI показуй безпечний статус конфігурації.
- IP та інші чутливі ідентифікатори зберігай лише в мінімально потрібному вигляді; не погіршуй наявне хешування або приватність аналітики.

## Перевірка

- Для локальної логіки запускай сфокусовані тести, потім за ризиком `npm test`, `npm run lint` і `npm run build` у `services/naradadruk`.
- Для шаблону Telegram перевіряй як позитивні сценарії, так і пропуск звичайного допису, draft-by-default, невалідну ціну/варіанти, відсутнє фото та повторну обробку.
- Для schema/worker змін окремо перевіряй `npx prisma validate`, schema push/seed на тестовій БД і одноразовий запуск потрібного worker-а.
- Якщо локально немає Docker, не стверджуй, що image або container перевірено. Чітко відділяй підтверджені тести/build/config checks від неперевіреного Docker runtime.
- Для UI-змін роби візуальну перевірку ключового потоку на mobile і desktop, якщо середовище дозволяє.

## Версія, changelog, commit і deploy

- Після завершеної зміни виконай у корені `node scripts/version.js patch` і додай новий запис на початок `changelog.json`.
- Для non-round версій `x.y.zz`, де `zz != 00`, використовуй один короткий нейтральний пункт без внутрішніх технічних або адмінських деталей.
- За наявності паралельного WIP коміть лише файли своєї задачі, `version.json` і `changelog.json`. Не включай решту NaradaDruk diff навіть якщо вона стосується того самого продукту.
- Після успішного commit і push онови тільки NaradaDruk через `/Users/andriimarchenko/.codex/scripts/paste-server-update-command.sh 'bash scripts/server-update.sh naradadruk'` та дочекайся завершення helper-а.
- Для runtime/env-only запиту використовуй `bash scripts/server-update.sh naradadruk --no-build`; для явного image refresh — `bash scripts/server-update.sh naradadruk --pull`; інакше використовуй стандартний rebuild.
- Успіх сервера підтверджуй лише за exit code `0` і зеленим HUD `Оновлення завершено`. Якщо SSH-вкладки немає, вона неоднозначна або update впав, повідом точний блокер і ручну команду; не відкривай SSH і не вводь пароль самостійно.
- Короткий запит `онови Narada Druk` є deployment-only: одразу запускай стандартний сервісний update без аналізу git, версії, changelog чи змін коду.
